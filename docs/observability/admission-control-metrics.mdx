The admission-control metrics show why requests are rejected and how close each model is to its configured occupancy and concurrency limits.

## Metrics

| Metric | Type | Labels | Meaning |
| --- | --- | --- | --- |
| `hivenet_admission_rejections_total` | Counter | `reason`, `model` | Requests rejected by an admission gate |
| `hivenet_admission_occupancy_tokens` | Gauge | `model` | This router's current weighted in-flight token sum |
| `hivenet_admission_budget_tokens` | Gauge | `model` | Effective global budget: `HIVENET_ROUTER_ADMIT_FRACTION × admit_budget_tokens × healthy_replicas`, or × the engines' summed KV capacity when `admit_budget_tokens` is unset. With `--sync-store=valkey` this is the site-wide budget, shared through credits |
| `hivenet_admission_inflight_requests` | Gauge | `model` | This router's current in-flight request count |
| `hivenet_admission_max_inflight` | Gauge | `model` | Full-pool request backstop after healthy-replica scaling, including the default backstop when applicable; `0` means no count backstop |

The global occupancy controller updates all four gauges when a request is admitted, released, adjusted to exact input usage, or grown by streamed output. The healthy-replica count is recomputed for each admission and floored at `1`, so the budget and backstop gauges follow the live serving pool.

With a [shared occupancy pool](/deploy/multiple-routers), the occupancy and in-flight gauges record this router's reservations. The budget and backstop gauges report the full-pool limits most recently observed by its controller, not the credits currently available to that router. Do not sum these limit gauges across routers.

For a site-wide utilization view, sum the local reservations from every router in the same site for the same model and compare them with one current, consistent full-pool limit. Keep sites and models separate, and check that the routers agree on their limits. A single router's occupancy-to-budget ratio measures its reservations relative to the full pool; it is not site utilization or a measure of its remaining credits. This differs from engine metrics repeated by several routers, which must be [deduplicated](/observability/prometheus-metrics#engine-histograms).

Per-tenant RPM rejects also increment `hivenet_tenant_rate_limited_total` in addition to the unified `b4_rpm` reason below.

### Rejection reasons

| `reason` | Gate and response |
| --- | --- |
| `b1` | Per-request input-token or image cap; HTTP `400 input_too_long` |
| `b2` | Occupancy budget, request-count backstop, or unavailable shared-pool credits; HTTP `429 concurrency_limit_exceeded` |
| `b3` | Front-door `shed_if` pressure gate; HTTP `429 concurrency_limit_exceeded` |
| `b4_occupancy` | Serverless per-key occupancy share; HTTP `429 rate_limit_exceeded` |
| `b4_itpm` | Serverless per-key input tokens per minute; HTTP `429 rate_limit_exceeded` |
| `b4_otpm` | Serverless per-key output tokens per minute; HTTP `429 rate_limit_exceeded` |
| `b4_rpm` | Requests per minute; HTTP `429 rate_limit_exceeded` |

## PromQL examples

Scope selectors to the intended site using your Prometheus scrape labels. The utilization expressions below operate on each router's matching series. The rejection examples aggregate the selected routers by model and reason; keep separate sites in separate queries or retain their scrape labels in the grouping.

### Occupancy utilization

```promql
hivenet_admission_occupancy_tokens
  / hivenet_admission_budget_tokens
```

Exclude a zero or unset budget when using this expression in an alert:

```promql
(
  hivenet_admission_occupancy_tokens
    / hivenet_admission_budget_tokens
)
and
hivenet_admission_budget_tokens > 0
```

### In-flight concurrency utilization

```promql
(
  hivenet_admission_inflight_requests
    / hivenet_admission_max_inflight
)
and
hivenet_admission_max_inflight > 0
```

### Rejections by gate

```promql
sum by (reason, model) (
  rate(hivenet_admission_rejections_total[5m])
)
```

### Front-door shed rate

```promql
sum by (model) (
  rate(hivenet_admission_rejections_total{reason="b3"}[5m])
)
```

### Serverless per-key gate pressure

```promql
sum by (reason, model) (
  rate(hivenet_admission_rejections_total{reason=~"b4_.*"}[5m])
)
```

The rejection counter has no `tenant_id` or `key_id` label, so it can show that a per-key gate is firing but cannot identify the individual key. Correlate the time window with tenant failure and token-limit metrics or audit records.

## Interpret the signals

- High occupancy utilization with rising `b2` can indicate token-budget pressure, but also check the request-count backstop. In a multi-router deployment, use the site-wide view described above and inspect credit availability and sync-store health; a router can reject work while its local occupancy ratio is low.
- Rising `b3` means the configured live-engine pressure threshold was crossed. Compare the reported signals with the threshold and site-wide occupancy; a low local occupancy ratio alone does not establish spare capacity.
- Sustained `b4_itpm`, `b4_otpm`, or `b4_occupancy` can indicate abusive traffic or undersized serverless key limits.
- A nonzero `max_inflight` with high concurrency utilization can bind before the token budget does when requests are small.

See [Admission control](/routing/admission-control) for gate order, reservation behavior, and client-facing errors.
