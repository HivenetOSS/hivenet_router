title: "Engine Metrics"
---

Mycoroute scrapes the inference engine's `/metrics` endpoint every 500 ms (configurable via `--engine-sample-interval`) and forwards the results to the router inside each routing-signal push. The router re-exports the data as Prometheus metrics under the `mycoroute_agent_engine_*` namespace.

Pointer fields in `BackendMetrics` are `nil` when an engine does not expose a particular metric — the router never emits a false-zero series in that case.

## Metric Availability by Engine

| Metric | vLLM | SGLang | llama.cpp |
|--------|------|--------|-----------|
| `kv_cache_utilization` | ✓ | ✓ | ✓ |
| `running_requests` | ✓ | ✓ | ✓ |
| `waiting_requests` | ✓ | ✓ | ✓ |
| `preemptions_total` | ✓ | — | — |
| `avg_ttft_seconds` | ✓ | ✓ | ✓ |
| `p90_ttft_seconds` | ✓ | ✓ | ✓ |
| `ttft_seconds` histogram | ✓ | ✓ | ✓ |
| `avg_itl_seconds` | ✓ | — | ✓ |
| `p90_itl_seconds` | ✓ | — | ✓ |
| `itl_seconds` histogram | ✓ | — | ✓ |
| `request_prompt_tokens` histogram | ✓ | — | — |
| `request_generation_tokens` histogram | ✓ | — | — |
| `request_success_total` (finish reason) | ✓ | — | — |
| `predicted_tps` | — | — | ✓ |
| `prompt_tps` | — | — | ✓ |

Requires `--metrics` for llama.cpp and `--enable-metrics` for SGLang at server launch.

## KV Cache Utilization

**What it measures:** The fraction of the pre-allocated GPU KV-cache currently in use (0.0–1.0). The KV-cache holds the key/value attention states for every active request. When it fills up, the engine must evict (preempt) in-flight requests to free space, causing latency spikes. This is the single most important saturation signal for routing.

**Source:** `vllm:kv_cache_usage_perc` · `sglang:token_usage` · `llamacpp:kv_cache_usage_ratio`

```promql
# KV cache usage by agent
mycoroute_agent_engine_kv_cache_utilization{peer_id="12D3Koo0..."}

# Agents with high KV cache pressure (>85%)
mycoroute_agent_engine_kv_cache_utilization > 0.85

# Average by region
avg by (region) (mycoroute_agent_engine_kv_cache_utilization)
```

**Interpretation:**

| Range | Status | Action |
|-------|--------|--------|
| 0–60% | Healthy | Can accept more requests |
| 60–85% | Moderate pressure | Monitor closely |
| 85–95% | High pressure | Risk of preemptions |
| >95% | Critical | Severe preemptions expected |

## Request Queue

**What it measures:** Two complementary counts that describe where requests are in the engine pipeline.

- **Running requests** — requests that the engine is actively processing (GPU is working on them). This directly maps to batch size and GPU utilization.
- **Waiting requests** — requests held in the scheduler queue, waiting for a slot in the running batch. Non-zero means the engine is saturated and new arrivals are being buffered. Route away from agents with a growing waiting count.

**Source:** `vllm:num_requests_running` / `vllm:num_requests_waiting` · `sglang:num_running_reqs` / `sglang:num_queue_reqs` · `llamacpp:requests_processing` / `llamacpp:requests_deferred`

```promql
# Running requests
mycoroute_agent_engine_running_requests{peer_id="12D3Koo0..."}

# Waiting requests
mycoroute_agent_engine_waiting_requests{peer_id="12D3Koo0..."}

# Total queue depth
mycoroute_agent_engine_running_requests + mycoroute_agent_engine_waiting_requests
```

## Preemptions

**What it measures:** The cumulative number of requests that the engine has evicted from the GPU mid-flight due to KV-cache pressure. A preempted request is paused, its KV-cache state is swapped out (or recomputed), and it restarts from scratch — causing a visible latency spike for that user. A rising preemption rate is a leading indicator that `kv_cache_utilization` is too high.

**Source:** `vllm:num_preemptions_total` (vLLM only — SGLang and llama.cpp have no preemption mechanism)

```promql
# Cumulative preemption count (gauge, resets on engine restart)
mycoroute_agent_engine_preemptions_total{peer_id="12D3Koo0..."}

# Preemption rate (events/sec over 5-minute window)
rate(mycoroute_agent_engine_preemptions_total[5m])

# Agents with high preemption rate
rate(mycoroute_agent_engine_preemptions_total[5m]) > 0.1
```

**Impact:** Preemptions cause latency spikes and reduced throughput. A non-zero rate alongside high `kv_cache_utilization` confirms KV-cache thrashing.

## Time to First Token (TTFT)

**What it measures:** How long it takes from when a request enters the engine until the first output token is generated. This is the latency a user perceives as "waiting for the response to start". High TTFT is typically caused by a large waiting queue, long prompt prefill, or a cold model load.

Three complementary series are exported:

| Metric | Description |
|--------|-------------|
| `mycoroute_agent_engine_avg_ttft_seconds` | Running average (histogram sum / count) |
| `mycoroute_agent_engine_p90_ttft_seconds` | 90th-percentile scalar — used directly by the routing policy evaluator |
| `mycoroute_agent_engine_ttft_seconds` | Full histogram — use `histogram_quantile()` for correct fleet-wide percentiles |

**Source:** `vllm:time_to_first_token_seconds` · `sglang:time_to_first_token_seconds` · `llamacpp:time_to_first_token_seconds`

```promql
# Average TTFT
mycoroute_agent_engine_avg_ttft_seconds{peer_id="12D3Koo0..."}

# P90 TTFT (per-peer scalar)
mycoroute_agent_engine_p90_ttft_seconds{peer_id="12D3Koo0..."}

# Fleet-wide P90 TTFT (correct aggregation over the histogram)
histogram_quantile(0.9, sum by (le) (rate(mycoroute_agent_engine_ttft_seconds_bucket[5m])))
```

**Targets:**

| Metric | Target | Warning |
|--------|--------|---------|
| Avg TTFT | < 100 ms | > 200 ms |
| P90 TTFT | < 200 ms | > 500 ms |

## Inter-Token Latency (ITL)

**What it measures:** The time between consecutive output tokens during the generation (decode) phase. This determines the perceived streaming speed — a high ITL means the response appears to pause or stutter mid-generation. High ITL is usually caused by GPU compute saturation or a very large running batch.

Three complementary series are exported:

| Metric | Description |
|--------|-------------|
| `mycoroute_agent_engine_avg_itl_seconds` | Running average (histogram sum / count) |
| `mycoroute_agent_engine_p90_itl_seconds` | 90th-percentile scalar |
| `mycoroute_agent_engine_itl_seconds` | Full histogram |

**Source:** `vllm:inter_token_latency_seconds` · `llamacpp:time_per_output_token_seconds`
*(SGLang does not expose an ITL histogram — these metrics will be absent for SGLang agents.)*

```promql
# Average ITL
mycoroute_agent_engine_avg_itl_seconds{peer_id="12D3Koo0..."}

# P90 ITL (per-peer scalar)
mycoroute_agent_engine_p90_itl_seconds{peer_id="12D3Koo0..."}

# Fleet-wide P90 ITL
histogram_quantile(0.9, sum by (le) (rate(mycoroute_agent_engine_itl_seconds_bucket[5m])))
```

**Targets:**

| Metric | Target | Warning |
|--------|--------|---------|
| Avg ITL | < 20 ms | > 50 ms |
| P90 ITL | < 50 ms | > 100 ms |

## Request Shape Histograms (vLLM only)

**What they measure:** The distribution of request sizes, split into two dimensions:

- **Prompt tokens** — how many input tokens the model received. Large prompts (long system prompts, RAG context) consume more KV-cache and increase TTFT.
- **Generation tokens** — how many output tokens the model produced. Longer generations hold KV-cache slots longer, reducing available capacity for concurrent requests.

These histograms drive the workload-shape heatmap panels on the Inference Engine dashboard.

**Source:** `vllm:request_prompt_tokens` · `vllm:request_generation_tokens`

```promql
# Average prompt length (tokens)
histogram_quantile(0.5, sum by (le) (rate(mycoroute_agent_engine_request_prompt_tokens_bucket[5m])))

# P90 generation length (tokens)
histogram_quantile(0.9, sum by (le) (rate(mycoroute_agent_engine_request_generation_tokens_bucket[5m])))
```

## Request Finish Reasons (vLLM only)

**What it measures:** How requests completed on the engine, broken down by finish reason. A `stop` finish means the model produced a natural end-of-sequence token. A `length` finish means the request hit the `max_tokens` limit before the model finished. An `abort` finish means the request was cancelled (client disconnect, timeout, or preemption). Tracking this breakdown reveals whether capacity limits are truncating responses or clients are abandoning slow requests.

**Source:** `vllm:request_success_total{finished_reason=...}`

```promql
# Request completion rate by finish reason
rate(mycoroute_agent_engine_request_success_total[5m])

# Abort rate (client disconnects / timeouts)
rate(mycoroute_agent_engine_request_success_total{finished_reason="abort"}[5m])

# Length-truncation rate (max_tokens hit)
rate(mycoroute_agent_engine_request_success_total{finished_reason="length"}[5m])
```

---

## Token Throughput (llama.cpp only)

**What they measure:** Real-time token processing rates measured over the last second:

- **`predicted_tps`** — how many output tokens per second the engine is generating (decode throughput). Higher is better; a drop here under stable load indicates GPU contention.
- **`prompt_tps`** — how many prompt tokens per second the engine is ingesting (prefill throughput). Useful for diagnosing slow prefill on long-context requests.

**Source:** `llamacpp:predicted_tokens_seconds` · `llamacpp:prompt_tokens_seconds`
*(These metrics are unique to llama.cpp — they are absent for vLLM and SGLang agents.)*

```promql
# Token generation throughput (tokens/sec)
mycoroute_agent_engine_predicted_tps{peer_id="12D3Koo0..."}

# Prompt ingestion throughput (tokens/sec)
mycoroute_agent_engine_prompt_tps{peer_id="12D3Koo0..."}

# Average generation throughput by engine
avg by (engine) (mycoroute_agent_engine_predicted_tps)
```

## Engine-Specific Routing

### Exclude Overloaded Agents

```yaml
routing_policy:
  match:
    engine: "vllm"
  exclude_if:
    kv_cache_utilization: { gt: 0.85 }
    waiting_requests: { gt: 20 }
  strategy: "least-loaded"
```

### Preemption-Aware Routing

```yaml
routing_policy:
  match:
    engine: "vllm"
  exclude_if:
    kv_cache_utilization: { gt: 0.80 }
  strategy: "least-loaded"
```

### TTFT-Optimized Routing

```yaml
routing_policy:
  match:
    engine: "vllm"
  exclude_if:
    p90_ttft_seconds: { gt: 0.2 }
  strategy: "least-loaded"
```

## Alerting Rules

### High KV Cache

```yaml
- alert: HighKVCache
  expr: mycoroute_agent_engine_kv_cache_utilization > 0.9
  for: 2m
  labels:
    severity: warning
  annotations:
    summary: "High KV cache usage on {{ $labels.peer_id }}"
```

### High Preemption Rate

```yaml
- alert: HighPreemptionRate
  expr: rate(mycoroute_agent_engine_preemptions_total[5m]) > 0.2
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "High preemption rate on {{ $labels.peer_id }}"
```

### TTFT Degradation

```yaml
- alert: TTFTDegradation
  expr: mycoroute_agent_engine_p90_ttft_seconds > 0.5
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "TTFT degradation detected on {{ $labels.peer_id }}"
```

## Troubleshooting

### High Preemptions

**Cause:** KV-cache pressure — running batch is too large for the available KV-cache allocation.

**Diagnosis:**

```promql
mycoroute_agent_engine_kv_cache_utilization > 0.9
rate(mycoroute_agent_engine_preemptions_total[5m]) > 0.1
```

**Resolution:** Lower the routing gate threshold so the agent is excluded sooner:

```yaml
exclude_if:
  kv_cache_utilization: { gt: 0.80 }
```

### High TTFT

**Cause:** Queue buildup (many waiting requests) or cold model loading.

**Diagnosis:**

```promql
mycoroute_agent_engine_waiting_requests > 10
mycoroute_agent_engine_avg_ttft_seconds > 0.5
```

**Resolution:**

```yaml
exclude_if:
  waiting_requests: { gt: 5 }
  p90_ttft_seconds: { gt: 0.3 }
```

### Missing Metrics for llama.cpp

Ensure the server is started with `--metrics`:

```bash
./llama-server -m model.gguf -a "ModelAlias" --host 0.0.0.0 --port 8888 --metrics
```

### Missing Metrics for SGLang

Ensure the server is started with `--enable-metrics`:

```bash
python -m sglang.launch_server --model-path meta-llama/Llama-3-8B-Instruct --enable-metrics
```
