Use Mycoroute’s administration API to inspect and change operational state.

The admin API includes endpoints for:

- router and agent health
- model discovery without tenant filtering
- detailed routing state
- persistent and in-memory storage inspection
- policy reload and runtime replacement
- Prometheus metrics
- dynamic API-key management

<Warning>
  Treat `/admin/*` as a privileged control-plane surface.

  Administrative endpoints can expose tenant identifiers, model access, quotas, agent metadata, infrastructure labels, routing state, and operational history. Some endpoints can change policy or API-key state immediately.
</Warning>

## Base URL

The admin API uses the router’s main HTTP port.

```text
http://<router-host>:8080/admin
```

The Docker Compose stack maps the router API to host port `8888`:

```text
http://<router-host>:8888/admin
```

Examples on this page use:

```text
http://localhost:8080
```

## Public health endpoint

The router also exposes a public liveness endpoint outside `/admin`:

```text
GET /health
```

```bash
curl http://localhost:8080/health
```

Expected response:

```json
{
  "status": "ok"
}
```

This endpoint is intentionally unauthenticated and only confirms that the HTTP process is running.

It does not report:

- agent count
- model availability
- queue state
- backend health
- storage health
- routing readiness

Use `GET /admin/health` for an operational view.

## Admin authentication

Administrator authentication is configured separately from client inference authentication.

| Admin mode | Behavior |
| --- | --- |
| `none` | No admin credential is checked; requires the explicit insecure startup override |
| `api-key` | Requires a raw key from `mycoroute_ADMIN_API_KEYS` |

A protected request uses:

```http
Authorization: Bearer <admin-api-key>
```

For example:

```bash
curl http://localhost:8080/admin/health \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

### Secure-by-default startup

The router refuses to start when administrator mode is `none` unless you explicitly set:

```bash
export mycoroute_ALLOW_INSECURE_ADMIN=true
```

Use that override only for isolated local development or testing.

A protected administrator configuration resembles:

```yaml
api:
  mode: api-key
  keys:
    - key_hash: "<client-key-sha256>"
      metadata:
        owner: "client-tenant"

admin:
  mode: api-key
```

Set the administrator key separately:

```bash
export mycoroute_ADMIN_API_KEYS="<raw-admin-key>"
```

<Warning>
  Client API keys do not automatically grant administrator access.

  Administrator keys do not grant client inference access unless the same raw value is also configured separately as a client key.
</Warning>

See [Authentication overview](/security/authentication-overview) for the complete trust-boundary model.

## HTTP semantics

### Content type

Send JSON mutations with:

```http
Content-Type: application/json
```

### Request IDs

Admin responses do not currently use the same request-ID and tracing middleware as the client inference endpoints.

Do not depend on `X-Request-ID` or `traceparent` being present on every `/admin/*` response.

### Admin request-body limits

Administrator JSON mutations use endpoint-specific limits that are separate from `mycoroute_MAX_REQUEST_BYTES`:

| Operation | Maximum body size |
| --- | --: |
| Policy update | 1 MiB |
| Create or update one dynamic key | 1 MiB |
| Replace the complete dynamic-key registry | 16 MiB |

Requests above these limits currently return HTTP `400` with a simple error body from the administration handler. They do not use the `/v1/*` structured Mycoroute error envelope, and raising `mycoroute_MAX_REQUEST_BYTES` does not change these limits.

### Errors

Most admin handlers use plain JSON or plain HTTP error text rather than the structured inference error envelope.

Check both:

- HTTP status
- response body

when automating the API.

## Endpoint summary

### Health and state

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/admin/health` | Operational router and agent health |
| `GET` | `/admin/models` | Complete model catalog |
| `GET` | `/admin/models/{model}` | Complete detail for one model |
| `GET` | `/admin/routing-table` | Detailed agent and routing state |
| `GET` | `/admin/in-memory-db` | Current in-memory key/value state |
| `GET` | `/admin/disk-db` | Persistent key/value state |
| `GET` | `/admin/disk-db/{key}` | One persistent record |
| `GET` | `/admin/disk-db-stats` | Persistent-store counts and size |
| `GET` | `/admin/metrics` | Redirect to Prometheus metrics server |

### Policy management

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/admin/policy` | Current policy and source files |
| `PUT` | `/admin/policy` | Replace the in-memory policy from JSON |
| `POST` | `/admin/policy/reload` | Reload policy files from disk |

### Dynamic API keys

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/admin/api-keys` | List metadata for dynamic key entries |
| `GET` | `/admin/api-keys/version` | Read the registry version |
| `PUT` | `/admin/api-keys/{id}` | Create or update one key |
| `DELETE` | `/admin/api-keys/{id}` | Delete one key |
| `POST` | `/admin/api-keys/replace` | Replace the complete registry |

Dynamic key endpoints are available only when client authentication mode is:

```text
dynamic
```

## Operational health

```text
GET /admin/health
```

```bash
curl http://localhost:8080/admin/health \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

A healthy response resembles:

```json
{
  "status": "healthy",
  "total_agents": 2,
  "healthy_agents": 2,
  "queue_length": 0,
  "timestamp": 1760000000,
  "agents": [
    {
      "peer_id": "12D3KooW...",
      "model": "meta-llama/Llama-3.1-8B-Instruct",
      "engine": "vllm",
      "version": "dev",
      "capacity": 32,
      "region": "EU-Primary",
      "is_healthy": true,
      "last_seen": 1760000000
    }
  ]
}
```

Possible top-level states include:

| Status | Meaning |
| --- | --- |
| `healthy` | At least one agent is registered and every registered agent is healthy |
| `degraded` | No agents are registered, or some registered agents are unhealthy |

The endpoint reports a broad router-wide summary. It does not prove that one particular model is routable.

`queue_length` is the length of the router’s global pending-request channel. It is not the per-model capacity wait queue and does not include requests already forwarded to agents.

For model readiness, combine:

- `/admin/health`
- `/admin/models/{model}`
- `/admin/routing-table`
- active routing policies

## Complete model catalog

```text
GET /admin/models
GET /admin/models/{model}
```

These endpoints use the same response shape as:

```text
GET /v1/models
GET /v1/models/{model}
```

but do not apply tenant model filtering.

List every registered model:

```bash
curl http://localhost:8080/admin/models \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

Read one model:

```bash
curl \
  "http://localhost:8080/admin/models/openai/gpt-oss-20b" \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

Use the public `/v1/models` endpoints to confirm what a specific client API key can see.

See [Models](/api/models) for the complete response reference.

The response groups data into:

| Object | Purpose |
| --- | --- |
| `metadata` | Static registration information |
| `status` | Current health, heartbeat, and active load |
| `universal` | Request, token, failure, and latency history |
| `engine` | Backend-specific live engine signals |
| `hardware` | CPU, memory, and GPU state |

Use the routing table to debug:

- model and capability registration
- policy metadata
- capacity
- health
- success rate
- SRTT and RTTVAR
- KV cache and engine queues
- GPU, CPU, and memory pressure

Filter one model:

```bash
curl http://localhost:8080/admin/routing-table \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq '.agents[]
      | select(
          .metadata.model ==
          "meta-llama/Llama-3.1-8B-Instruct"
        )'
```

## Inspect the in-memory database

```text
GET /admin/in-memory-db
```

```bash
curl http://localhost:8080/admin/in-memory-db \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

The endpoint returns current key/value records from the router’s in-memory BadgerDB.

Keys and values are exposed as strings when they contain valid UTF-8. Otherwise they are encoded as:

```text
base64:<encoded-value>
```

Use this endpoint for debugging current agent and session state. Do not build long-lived automation against internal key names or serialized values.

<Warning>
  This response can expose sensitive internal state. Restrict access and avoid copying it into unprotected support tickets or public issue reports.
</Warning>

## Inspect the persistent database

```text
GET /admin/disk-db
```

```bash
curl http://localhost:8080/admin/disk-db \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

The endpoint returns all records from the persistent BadgerDB.

This store can contain:

- agent request and token history
- smoothed latency state
- failure and disconnection history
- persistent daily token-quota counters when the Badger quota backend is enabled

Binary keys and values use the same `base64:` representation as the in-memory database endpoint.

Avoid polling the complete database frequently. The handler reads and serializes every record.

## Read one persistent key

```text
GET /admin/disk-db/{key}
```

```bash
curl \
  "http://localhost:8080/admin/disk-db/<key>" \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

A response resembles:

```json
{
  "key": "<key>",
  "value": "<value>"
}
```

A missing key returns HTTP `404`.

URL-encode path separators, spaces, and other reserved characters in the key.

## Persistent database statistics

```text
GET /admin/disk-db-stats
```

```bash
curl http://localhost:8080/admin/disk-db-stats \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

A response resembles:

```json
{
  "total_keys": 142,
  "database_size_bytes": 8388608,
  "last_updated": "2026-04-11T12:00:00Z"
}
```

`last_updated` is generated when the stats request is processed. It is not the timestamp of the most recent database write.

## Metrics redirect

```text
GET /admin/metrics
```

The handler redirects to:

```text
http://<router-host>:2112/metrics
```

```bash
curl -L http://localhost:8080/admin/metrics \
  -H "Authorization: Bearer <admin-api-key>"
```

The separate metrics server does not have built-in authentication.

Protect port `2112` through network controls or a trusted proxy.

## Read the current policy

```text
GET /admin/policy
```

```bash
curl http://localhost:8080/admin/policy \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

A response includes:

```json
{
  "policy": {
    "routing_policy": {
      "strategy": "least-loaded",
      "max_tries": 3
    }
  },
  "file": "/etc/mycoroute/policy.yaml",
  "model_dir": "/etc/mycoroute/policies"
}
```

When no policy file or directory is configured, the file values are empty strings and the active policy is Mycoroute’s built-in least-loaded policy.

The endpoint reports the current global policy. It does not return the complete resolved per-model policy map.

## Replace the in-memory policy

```text
PUT /admin/policy
```

The body is JSON, not YAML.

```bash
curl -X PUT \
  http://localhost:8080/admin/policy \
  -H "Authorization: Bearer <admin-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "routing_policy": {
      "match": {
        "region": "EU-France"
      },
      "exclude_if": {
        "success_rate": {
          "lt": 0.95
        }
      },
      "strategy": "least-loaded",
      "max_tries": 3
    }
  }'
```

A successful response is:

```json
{
  "status": "ok"
}
```

The new policy becomes active immediately.

<Warning>
  The update changes the policy in memory. It does not write the policy back to disk.

  A later file reload or router restart can replace the runtime policy.
</Warning>

The policy JSON must pass the same validation as a policy loaded from YAML.

## Reload policy files

```text
POST /admin/policy/reload
```

```bash
curl -X POST \
  http://localhost:8080/admin/policy/reload \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

A successful response resembles:

```json
{
  "status": "ok",
  "message": "policy reloaded"
}
```

If both are configured:

```text
--policy-file
--policy-model-dir
```

and the model directory contains `_default.yaml`, the directory’s default policy replaces the standalone global file.

The reload is atomic. When a replacement file is invalid, the current valid policy remains active.

```text
GET /admin/api-keys
```

```bash
curl http://localhost:8080/admin/api-keys \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

A response resembles:

```json
{
  "version": "rev_00000042",
  "items": [
    {
      "id": "acme-prod",
      "key_preview": "sk-...a1b2",
      "owner": "acme-corp",
      "name": "Production application",
      "enabled": true,
      "expires_at": null,
      "allowed_models": [
        "meta-llama/Llama-3.1-8B-Instruct"
      ],
      "quota": {
        "requests_per_minute": 100,
        "tokens_per_day": 500000
      }
    }
  ]
}
```

Raw API keys and full hashes are not returned.

The list is sorted by key ID.

## Read the dynamic registry version

```text
GET /admin/api-keys/version
```

```bash
curl http://localhost:8080/admin/api-keys/version \
  -H "Authorization: Bearer <admin-api-key>" \
  | jq .
```

Response:

```json
{
  "version": "rev_00000042"
}
```

The version is an opaque string compared lexicographically.

Use a convention such as fixed-width counters or sortable timestamps:

```text
rev_00000042
2026-04-11T12:00:00Z
```

Avoid values whose lexical and numeric order differ:

```text
9
10
```

Lexicographically, `10` sorts before `9`.

## Create or update a dynamic key

```text
PUT /admin/api-keys/{id}
```

```bash
curl -X PUT \
  http://localhost:8080/admin/api-keys/acme-prod \
  -H "Authorization: Bearer <admin-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "version": "rev_00000043",
    "key_hash": "<sha256-of-raw-key>",
    "key_preview": "sk-...a1b2",
    "owner": "acme-corp",
    "name": "Production application",
    "enabled": true,
    "allowed_models": [
      "meta-llama/Llama-3.1-8B-Instruct"
    ],
    "quota": {
      "requests_per_minute": 100,
      "tokens_per_day": 500000
    }
  }'
```

Accepted fields include:

| Field | Required | Purpose |
| --- | --- | --- |
| `version` | Yes | Registry revision for ordering updates |
| `key_hash` | Yes | SHA-256 hash of the raw API key |
| `key_preview` | No | Masked display value |
| `owner` | Yes | Tenant identity used for quotas and metrics |
| `name` | No | Human-readable description |
| `enabled` | No | Whether the key can authenticate; defaults to `true` |
| `expires_at` | No | Expiration time; Unix seconds or RFC 3339 |
| `allowed_models` | No | Model allowlist |
| `quota` | No | Flat or per-model quota configuration |

The raw API key is never sent to the registry. Hash it before making the request.

```bash
printf '%s' '<raw-api-key>' \
  | sha256sum
```

A successful update returns:

```json
{
  "status": "ok"
}
```

The change takes effect immediately.

curl -X DELETE \

```json

  "status": "ok"

```

The change takes effect immediately.

## Replace the complete dynamic registry

```text
POST /admin/api-keys/replace
```

Use this endpoint to repopulate the registry after a router restart or synchronize it from an external control service.

```bash
curl -X POST \
  http://localhost:8080/admin/api-keys/replace \
  -H "Authorization: Bearer <admin-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "version": "rev_00000045",
    "items": [
      {
        "id": "acme-prod",
        "key_hash": "<sha256-of-raw-key>",
        "key_preview": "sk-...a1b2",
        "owner": "acme-corp",
        "name": "Production application",
        "enabled": true,
        "allowed_models": [
          "meta-llama/Llama-3.1-8B-Instruct"
        ],
        "quota": {
          "requests_per_minute": 100,
          "tokens_per_day": 500000
        }
      }
    ]
  }'
```

A successful response is:

```json
{
  "status": "ok"
}
```

The replacement is atomic. Existing items remain active when the replacement fails validation.

<Warning>
  The dynamic registry is memory-only.

  A router restart removes all dynamic key entries. Repopulate the complete registry before expecting clients to authenticate.
</Warning>

## Dynamic version conflicts

Dynamic mutations compare their `version` with the registry’s current version.

A lower version is rejected with HTTP `409`:

```json
{
  "error": "stale version",
  "current_version": "rev_00000045"
}
```

Use a later version and retry.

Versions compare lexicographically, not numerically.

Equal versions are currently accepted. Use a strictly newer version for each distinct update so two different mutations do not share one revision.

## Common status codes

| Status | Typical meaning |
| --- | --- |
| `200` | Read or mutation succeeded |
| `307` | Metrics endpoint redirect |
| `400` | Invalid JSON, invalid policy, missing field, invalid key, invalid version, or oversized admin body |
| `401` | Missing or invalid administrator credential |
| `404` | Model, key, storage record, or mode-specific endpoint not found |
| `409` | Stale dynamic registry version |
| `500` | Internal storage, policy, or configuration failure |
| `503` | No API-key registry is available |

Admin errors are not guaranteed to use the same error envelope as inference endpoints.

For example, a stale version returns:

```json
{
  "error": "stale version",
  "current_version": "rev_00000045"
}
```

## Network protection

Do not expose the admin API directly to the public internet.

Use one or more of:

- a private network
- host or cloud firewall rules
- a reverse proxy with TLS
- a VPN
- an identity-aware proxy
- a separate operator ingress
- short-lived administrator credentials

The same HTTP listener serves inference and administration routes, so network controls must preserve application access while restricting `/admin/*` where possible.

## Troubleshooting

### Every admin request returns `401`

Check that:

- `admin.mode` is `api-key`
- `mycoroute_ADMIN_API_KEYS` is set in the router process
- the request sends `Authorization: Bearer <admin-api-key>`
- the admin key is not only configured as a client key
- the router was restarted after changing its environment

### The router refuses to start with admin mode `none`

This is the secure default.

For isolated local development only, set:

```bash
export mycoroute_ALLOW_INSECURE_ADMIN=true
```

For shared or production deployments, configure `admin.mode: api-key` and set `mycoroute_ADMIN_API_KEYS` instead.

### Dynamic key endpoints return `404`

Confirm client authentication mode is:

```text
dynamic
```

The endpoints are not registered in static `api-key` or `none` mode.

### A dynamic key disappears after restart

This is expected. The registry is memory-only.

Send the complete current state to:

```text
POST /admin/api-keys/replace
```

before applications resume authentication.

### A policy update disappears after restart

`PUT /admin/policy` changes only the in-memory policy.

Update the policy file or model-policy directory on disk, then use:

```text
POST /admin/policy/reload
```

### `/admin/metrics` does not return metrics

The endpoint redirects to port `2112`.

Use:

```bash
curl -L http://localhost:8080/admin/metrics
```

Check that the metrics port is reachable from the client following the redirect.

### Model discovery differs between admin and public endpoints

This normally means the client API key has:

- `allowed_models`
- `quota.per_model`

The admin view is complete. The public `/v1/models` view is filtered for the authenticated client.
