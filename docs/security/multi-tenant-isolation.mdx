When the routers of a site serve several customers, nothing outside the routers separates them. They must make sure one customer cannot use, observe or slow down another. This page describes what keeps tenants apart and how to turn it all on.

A **tenant** is the owner of an API key: `metadata.owner` for keys in `auth.yaml`, `owner` for keys pushed through `/admin/api-keys`. One tenant can have several keys.

## Turn on multi-tenant mode

Start every router of the site with `--multi-tenant` (`HIVENET_ROUTER_MULTI_TENANT=true`). It needs a salt secret and a protected metrics endpoint, and a site of several routers needs [shared counters](/deploy/multiple-routers) with a password:

```bash
openssl rand -base64 48 > /etc/hivenet-router/cache-salt.secret
openssl rand -hex 32 > /etc/hivenet-router/metrics.token

hivenet-router \
  --multi-tenant \
  --auth-config-file /etc/hivenet-router/auth.yaml \
  --cache-salt-secret-file /etc/hivenet-router/cache-salt.secret \
  --metrics-bearer-token-file /etc/hivenet-router/metrics.token \
  --sync-store valkey \
  --sync-valkey-addrs valkey:6379 \
  --sync-valkey-password-file /etc/hivenet-router/valkey.password \
  --sync-min-routers 3
```

Every router of a site must use the same salt secret: every agent serves every router, so a tenant's requests through any router must land in the same cache namespace.

`--multi-tenant` turns on these settings:

| Setting | Effect |
| --- | --- |
| `--require-model-allowlist` | A key with no model allowlist can call and list no model. Cannot be turned off |
| `--cache-salt` | Each tenant gets its own prefix-cache namespace on every engine that supports it. On by default; see the opt-out below |
| `--hide-agent-identity` | `GET /v1/models/{model}` leaves out agent peer IDs, organization, machine, version and last-seen time. Cannot be turned off |

The router refuses to start in multi-tenant mode when:

- API authentication mode is `none`, because every caller would be the same tenant
- admin authentication is disabled (`HIVENET_ROUTER_ALLOW_INSECURE_ADMIN`)
- `/metrics` listens on every interface without a bearer token
- `--sync-min-routers` is above `1` without `--sync-store=valkey`, because each router would then enforce every key's limits on its own
- `--sync-store=valkey` has no password (`--sync-valkey-password-file` or `HIVENET_ROUTER_SYNC_VALKEY_PASSWORD`): the store holds every tenant's usage
- the cache-salt secret is missing, shorter than 32 bytes, or equal to the JWT or key-store secret

Set `--sync-min-routers` to the number of routers of the site: the router has no other way to know it is one of several.

A `SIGHUP` reload that would break one of these rules is rejected, and the previous keys stay in force.

### Opt out of prefix-cache isolation

To run a multi-tenant router without prefix-cache isolation, for example while an engine does not support it, set `--cache-salt=false` (or `HIVENET_ROUTER_CACHE_SALT=false`) explicitly. The router then forwards bodies unchanged, logs a warning at startup, and counts every LLM agent in `hivenet_cache_isolation_gaps`. Tenants sharing an engine then share its prefix cache, so one tenant can infer another's prompts from response timing.

Each setting can also be used on its own, without `--multi-tenant`. See the [configuration reference](/reference/configuration-reference#tenant-isolation-settings).

## What isolates tenants

### Identity comes from the key

The tenant and key of a request come only from its credential. Headers such as `X-Tenant-ID` or body fields such as `user` change nothing. Every key has a key ID: the registry ID for dynamic keys, and an ID derived from `key_hash` for `auth.yaml` keys (`static-` followed by 16 hex characters). Key IDs and owners may not contain control characters.

### Limits are per key

Request-rate, daily-token and serverless token-rate limits are counted per key, against that key's own limits, and with shared counters across all the routers of the site. One key exhausting its budget never causes a `429` for another key, of the same tenant or another. A tenant with several keys can use up to the sum of their limits. See [API keys](/security/api-keys).

`hivenet_tenant_tokens_used_today` reports each tenant's usage today over all its keys that have a daily token budget; with shared counters every router reports the site total, so aggregate it with `max by (tenant_id)`.

### Keys reach only their models

With an allowlist required, a key can only use the models in its `models` / `allowed_models` list or its `quota.per_model` block. This applies to chat, messages, embeddings, reranking, semantic aliases, cross-site redirects and model discovery. See [Model restrictions](/security/model-restrictions).

### The prefix cache is isolated per tenant

Engines share cached prompt blocks between requests with the same prefix, so a faster first token can reveal that someone else sent the same prompt. The router sets a per-tenant `cache_salt` on requests to vLLM (every path) and SGLang (chat completions), turns llama.cpp's prompt cache off per request, and removes any `cache_salt` the client sent. An LLM agent left with a path it cannot isolate is logged and counted in `hivenet_cache_isolation_gaps`. See [Isolate tenants in the prefix cache](/deploy/agents/vllm#isolate-tenants-in-the-prefix-cache).

### Logs and metrics are attributable and protected

- Every authenticated audit record names its `tenant_id` and `key_id`. Records hold metadata only, never prompts, completions or credentials. The audit file is created with mode `0600`. See [Audit logging](/observability/audit-logging).
- Tenant metrics carry `tenant_id` and `key_id` labels. Require a bearer token on `/metrics` or bind it to a private address. See [Prometheus metrics](/observability/prometheus-metrics).

### The admin API stays with the operator

`/admin/*` uses its own keys, which are not API keys. Tenant keys never reach it, and its responses carry no CORS headers. There is no per-tenant admin role.

## Limits of this isolation

<Warning>
  Tenants share the router's capacity. Admission budgets, queues and agent slots are shared per model, so a burst from one tenant can make another wait or get a `429` or `503`. A key's `max_occupancy_share` caps how much of a model one key can hold in flight. A dedicated replica removes the sharing entirely.
</Warning>

- Prefix-cache isolation covers only what each engine supports: Ollama, custom backends, and `/v1/messages` on SGLang and llama.cpp are not isolated (see `hivenet_cache_isolation_gaps`).
- The operator of the router and of the agents can read prompts and completions. These controls separate tenants from each other, not from the operator.
- One budget for a whole tenant (across its keys and sites), and a key's maximum scope (`scope_max`), are not part of this release.

## Check the isolation

The repository's isolation checklist maps each control to the test that proves it. Run it with:

```bash
go test ./test/... -run 'TestIsolation|TestChecklist' -count=1
```

The checklist itself is `test/isolation/CHECKLIST.md`.
