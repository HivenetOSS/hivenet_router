Complete reference for the `auth.yaml` configuration file that manages API keys and access control.

## File Location

Pass with `--auth-config-file` flag (env: `mycoroute_AUTH_CONFIG`):

```bash
./bin/mycoroute-router --auth-config-file /etc/mycoroute/auth.yaml
```

If not set, both `/v1/*` and `/admin/*` default to `mode: none` (no authentication).

> **Dynamic mode:** For dynamic key management, set `mycoroute_AUTH_MODE=dynamic` — no `auth.yaml` is needed for API key definitions; the machines service pushes the registry at runtime via `/admin/api-keys/*`.
>
> Because those endpoints **are** the key-management surface, admin authentication is mandatory in dynamic mode. The router automatically elevates `admin.mode` to `api-key` and **requires** `mycoroute_ADMIN_API_KEYS` to be set; if it is missing, startup fails with `auth: admin section mode=api-key but mycoroute_ADMIN_API_KEYS env var is not set`. This auto-elevation only applies in dynamic mode — static (`api-key`) and `none` deployments still need an explicit `admin.mode` in `auth.yaml` to enable admin auth.

## Top-Level Structure

```yaml
api:
  mode: "none" | "api-key"
  keys: [...]        # only when mode=api-key

admin:
  mode: "none" | "api-key"
  # Admin keys are NOT stored here — see mycoroute_ADMIN_API_KEYS below
```

## api Section

Controls authentication for `/v1/*` inference endpoints.

```yaml
api:
  mode: "api-key"
  keys:
    - key_hash: "e3b0c44298fc1c149afbf4c8996fb924..."
      key_preview: "sk-...KJ4"
      metadata:
        name: "Production API"
        owner: "acme-corp"
        description: "Main production key"
        created_at: "22-04-2026"
        expires_at: "01-01-2027"   # optional; key rejected after this date (DD-MM-YYYY)
      models: []                   # empty = all models; non-empty = whitelist
      quota:
        requests_per_minute: 1000
        tokens_per_day: 1000000
```

### Key Entry Fields

| Field | Required | Description |
|-------|----------|-------------|
| `key_hash` | ✅ | SHA-256 hex of the raw key string |
| `key_preview` | ❌ | Masked form (`sk-...XXXX`) for operator identification; generated by `keygen`, omit only if adding a key manually |
| `metadata.name` | ✅ | Human-readable label |
| `metadata.owner` | ✅ | Tenant ID — used in Prometheus labels and audit logs |
| `metadata.description` | ❌ | Free-text note |
| `metadata.created_at` | ❌ | Creation date in DD-MM-YYYY format |
| `metadata.expires_at` | ❌ | Expiry date in DD-MM-YYYY format |
| `models` | ❌ | Model whitelist; empty list = unrestricted |
| `quota.requests_per_minute` | ❌ | RPM limit; 0 = unlimited. **Flat-shape only — mutually exclusive with `quota.per_model`** |
| `quota.tokens_per_day` | ❌ | Daily token budget; 0 = unlimited. **Flat-shape only — mutually exclusive with `quota.per_model`** |
| `quota.per_model` | ❌ | Per-model overrides — see [Per-model quotas](#per-model-quotas) below. **When present, replaces the two flat fields entirely** |
| `quota.per_model.<model>.requests_per_minute_per_replica` | ✅ (inside per_model entry) | Per-minute request rate **per healthy replica**; effective ceiling = this × live replicas. 0 = unlimited |
| `quota.per_model.<model>.tokens_per_day` | ✅ (inside per_model entry) | Per-model absolute daily token budget; 0 = unlimited |

### Per-model quotas

Flat `requests_per_minute` and `tokens_per_day` apply to *every model* the key
may call. That works while one tenant calls one model — but two models on the
same key usually have **different sustainable throughput** (a 27B serves
~50 RPM per replica, a small embeddings model serves thousands) and different
cost profiles. A flat ceiling forces you to either starve the fast model or
let the slow model get overwhelmed.

The `per_model` block lets you declare a **separate RPM and TPD per model**,
with the RPM expressed **per healthy replica** so it auto-scales as the fleet
grows or shrinks.

```yaml
quota:
  per_model:
    Qwen/Qwen3.6-27B:
      requests_per_minute_per_replica: 10
      tokens_per_day: 3_000_000
    Qwen/Qwen3.6-35B:
      requests_per_minute_per_replica: 5
      tokens_per_day: 2_000_000
    BAAI/bge-m3:
      requests_per_minute_per_replica: 1000
      tokens_per_day: 0                      # 0 = unlimited
```

#### Semantics

| Rule | Meaning |
|---|---|
| `per_model` present, flat fields **absent** | `per_model` is authoritative. The two shapes are **mutually exclusive on the same key** — the loader rejects a key that declares both. |
| Both fields **required** per entry | `requests_per_minute_per_replica` AND `tokens_per_day` must each be set on every entry. The loader rejects a partial entry — "forgot a field" must never silently mean "unlimited". |
| Strict enumeration — no wildcard | Every model the key may call must appear in `per_model`. A request to an unlisted model is **rejected** with `429 rate_limit_exceeded` ("no quota declared for model X on this API key") — never silently admitted, so a typo or a new fleet addition surfaces loudly. |
| `per_model` IS the model allow-list | `GET /v1/models` and `GET /v1/models/:model` are filtered to the keys of `per_model`. A caller only sees (and can introspect) the models they have a quota for; other tenants' models are invisible. No separate `models:` list needed for per-model keys — declaring a `per_model` entry is the single source of truth. An unlisted model returns `404` from `GET /v1/models/:model` (not `403`) so the catalog isn't leaked across tenants. |
| `0` on either knob | Means **unlimited** at that level, consistent with the flat shape. |
| Effective RPM at admission | `requests_per_minute_per_replica × healthy_replicas(model)`. Add an agent → every key's effective ceiling grows proportionally. Drain an agent → every key feels proportional pressure. |
| TPD is absolute | Not per-replica. Cost is a contract with the tenant; scaling the fleet must not silently grow the bill. |
| Zero healthy replicas | The RPM check is **skipped** entirely so the routing layer can return its real "no healthy backends" error instead of a misleading rate-limit message. |

#### Why per-replica RPM (instead of an absolute number)

A static `requests_per_minute: 50` on a key is a lie about reality: it caps the
key at 50 RPM regardless of whether you have 1 replica or 10. With 5 replicas
you've thrown away 80% of capacity. Per-replica + live replica count fixes
this:

| Live replicas | `requests_per_minute_per_replica: 10` resolves to |
|---|---|
| 1 | 10 RPM effective |
| 3 | 30 RPM effective |
| 5 | 50 RPM effective |
| 0 (drained) | Quota skipped — routing returns "no healthy backends" |

Operator mental model for splitting capacity across keys: "the 35B sustains
~50 RPM per replica. I have 3 production keys → each gets ~30% of a replica →
`requests_per_minute_per_replica: 15`." Operator arithmetic; no router-side
fairness math required.

#### Why no `requests_per_minute_max`

There is intentionally no absolute ceiling layered on top. Per-replica already
gives you the right scaling behaviour, and a hard cap would re-introduce the
"wasted capacity when the fleet grows" problem this shape exists to fix. If
you genuinely need an absolute cap for compliance reasons, issue a separate
key with `requests_per_minute_per_replica` set to the absolute number divided
by the smallest replica count you'll ever operate at.

#### Migration from the flat shape

The flat shape is **untouched** — existing keys keep working with no edit. To
migrate a single key, replace its `quota` block:

```yaml
# Before
quota:
  requests_per_minute: 100
  tokens_per_day: 5_000_000

# After
quota:
  per_model:
    Qwen/Qwen3.6-27B:
      requests_per_minute_per_replica: 10
      tokens_per_day: 3_000_000
    Qwen/Qwen3.6-35B:
      requests_per_minute_per_replica: 5
      tokens_per_day: 2_000_000
```

Then SIGHUP the router (`kill -HUP $(pgrep mycoroute-router)`) — the limiter's
in-process buckets are reset on reload, so the new shape takes effect on the
next request.

### Token Budget Enforcement

The daily token budget (`quota.tokens_per_day`) counts both prompt and
completion tokens against one per-tenant counter that resets at midnight UTC.
Enforcement follows the convention used by upstream providers — **admission
control up front, accounting after** — so it works correctly for streaming:

- **Front door (before queueing).** The router checks the *worst case* —
  estimated prompt tokens **plus** the requested `max_tokens` — against the
  remaining budget **without charging it**. If it cannot fit, the request is
  rejected immediately with `429 token_limit_exceeded` and **consumes no budget**,
  before any tokens are streamed (a streamed response cannot be cleanly rejected
  once its `200` and headers have been sent). Only an **admitted** request is
  charged: its prompt estimate now, its actual completion tokens after the
  response. `max_tokens` is only used to size this check; it is never deducted.
- **After the response.** The **actual** completion tokens are deducted once the
  response completes. For streaming responses this is post-hoc accounting (the
  bytes are already delivered), drawn from the backend's `usage` chunk when
  present (`stream_options.include_usage`) or estimated from the streamed text
  otherwise. Over-budget usage is reflected in the **next** request's check.

> The prompt-token estimate is exact for OpenAI-shaped bodies. For other dialects
> routed through the [passthrough](/api/chat-completions#how-the-passthrough-works)
> (e.g. Anthropic `/v1/messages`) it is best-effort — it does not see a top-level
> `system` prompt or non-text content blocks — so it may undercount the input
> side. A small per-message floor is still applied so image/tool-only prompts pass
> through the admission gate rather than bypassing it with a zero estimate. Set
> `tokens_per_day: 0` to disable token budgeting entirely.

#### Multimodal inputs (known limitation / future work)

Token counting happens in two places, and **only one** is affected by multimodal
(image/audio) content:

- **Post-hoc accounting (after the response) — already accurate.** The backend's
  `usage.prompt_tokens` counts image and audio tokens correctly, and the router
  uses that value for the actual budget deduction and for metrics. So billing and
  usage reporting for multimodal requests are already right.
- **Front-door admission (before sending) — text-only estimate.** The pre-queue
  check estimates from text content only (plus the per-message floor), so image
  and audio inputs are under-estimated *at admission*. The worst-case `max_tokens`
  gate and the pre-charge therefore reflect less than the true input size for
  multimodal requests.

"Adding multimodal token counting" would mean making the **pre-flight admission
estimate** aware of image/audio cost — i.e. estimating multimodal input size
*before* the request is sent. It is **not** a change to post-response accounting,
which is already correct.

This is non-trivial because image cost is **model-specific** (Anthropic, OpenAI,
and Qwen-VL each price images differently) and requires the image's pixel
dimensions — cheap to read for inline base64 data URIs, but for remote image URLs
it implies fetching the image (latency on the hot path and an SSRF surface). The
pragmatic first step, if/when this is pursued, is a conservative per-image /
per-audio-second floor in the estimator (over-estimates, so it never under-charges
the gate) rather than exact per-model formulas.

### Generating key_hash and key_preview

Use the built-in keygen command — it outputs a ready-to-paste YAML snippet:

```bash
./bin/mycoroute-router keygen --tenant acme-corp
```

Do not construct these values by hand unless you understand the format exactly.

### Model Whitelist

```yaml
# Unrestricted — key can request any model
models: []

# Restricted — only listed models allowed
models:
  - "meta-llama/Llama-3.1-8B-Instruct"
  - "BAAI/bge-m3"
```

Attempting to use a restricted key for an unlisted model returns `403`.

The same allow-list also filters the discovery endpoints: `GET /v1/models`
returns only the listed models, and `GET /v1/models/:model` returns `404`
for unlisted models (not `403`, so the cluster's full catalog isn't leaked
across tenants).

**Precedence with `quota.per_model`.** If the key declares
[per-model quotas](#per-model-quotas), the `per_model` map's keys are the
allow-list — any `models:` entry on the same key is ignored. This keeps the
per-model declaration as the single source of truth, so the discovery view
can't drift from what strict-enumeration admission will accept. For legacy
flat-quota keys, `models:` is honoured as before.

## admin Section

Controls authentication for `/admin/*` operational endpoints.

```yaml
admin:
  mode: "api-key"
```

When `mode: api-key`, admin keys must be supplied via the **environment variable** `mycoroute_ADMIN_API_KEYS` (comma-separated list of raw keys). They are never stored in this file.

```bash
export mycoroute_ADMIN_API_KEYS="admin-key-1,admin-key-2"
```

In requests, send via `Authorization: Bearer`:

```bash
curl -H "Authorization: Bearer admin-key-1" http://localhost:8080/admin/health
```

## Loading auth.yaml

### Initial Load

```bash
./bin/mycoroute-router --auth-config-file /etc/mycoroute/auth.yaml
```

### Hot Reload

Send SIGHUP to reload without restart:

```bash
kill -HUP $(pgrep mycoroute-router)
```

All changes to `auth.yaml` — new keys, revoked keys, updated quotas — take effect immediately.

## Security Considerations

1. **File permissions** — Set `0600` on `auth.yaml` (`chmod 600 /etc/mycoroute/auth.yaml`)
2. **Never store raw keys** — Only `key_hash` goes in the file
3. **Backup** — Include `auth.yaml` in encrypted backups
4. **Secrets manager** — For production, consider managing keys via HashiCorp Vault or AWS Secrets Manager
