Hivenet Router can reject an oversized request, shed new work when the serving pool is under pressure, or briefly park work when the configured occupancy budget is full. These checks run before the request enters the routing queue and before an inference backend receives it.

Admission control currently applies to the allowlisted LLM passthrough routes:

- `POST /v1/chat/completions`
- `POST /v1/messages`
- `POST /v1/messages/count_tokens`

The embeddings and reranking handlers do not run these policy admission checks.

## Configure a policy

Admission fields live at the top level of a global or per-model policy:

```yaml
models:
  - Qwen/Qwen3.6-27B-A3B

mode: reserved
max_input_tokens: 131072
images_max: 8
admit_budget_tokens: 262144
max_inflight: 16

routing_policy:
  match:
    engine: vllm
  strategy: least-loaded
```

All four numeric limits are optional. `0` or an omitted field disables that check. Negative values make policy validation fail.

| Field | Current behavior |
| --- | --- |
| `max_input_tokens` | Rejects a request when the router's estimated text prompt exceeds the limit |
| `images_max` | Rejects a request carrying more images than the limit |
| `admit_budget_tokens` | Limits the token-weighted sum of in-flight requests for the model |
| `max_inflight` | Limits the number of in-flight requests for the model |

<Note>
  The `max_input_tokens` request cap uses the router's simple text estimate. Occupancy and token-budget admission use a separate learned per-model tokens-per-byte estimate. It starts conservatively at one token per 3.2 bytes, includes OpenAI message text and an Anthropic top-level `system` prompt, and updates from exact backend `prompt_tokens` reports with an EWMA weight of `0.2`.

  Image content is counted separately by `images_max` because an image's model-specific token cost cannot be inferred from its byte size.
</Note>

## Request caps

The router resolves the effective policy for the requested model and checks text and image limits independently.

If either limit is exceeded, the router returns HTTP `400` with `input_too_long`:

```json
{
  "error": {
    "code": "input_too_long",
    "message": "input is 140000 tokens, over the model limit of 131072",
    "source": "router"
  }
}
```

Reducing only `max_tokens` does not fix this response. Reduce the input text or number of images.

## Occupancy budget

For each model, the router maintains an in-process occupancy total and in-flight request count. A request's initial footprint is:

```text
estimated input tokens + declared maximum output tokens
```

The declared output is `max_completion_tokens`, falling back to `max_tokens`. If neither field is present, the request initially reserves only its input estimate and the reservation grows as streamed output is observed.

The effective token budget is:

```text
floor(HIVENET_ROUTER_ADMIT_FRACTION × admit_budget_tokens)
```

`HIVENET_ROUTER_ADMIT_FRACTION` defaults to `0.90` and accepts values greater than `0` and at most `1`. Invalid values leave the default unchanged.

When the request would exceed the token budget or `max_inflight`, it waits for up to `HIVENET_ROUTER_ADMIT_PARK_TIMEOUT`. The default is `250ms`; `0` rejects immediately. The value uses Go duration syntax such as `100ms`, `2s`, or `1m`.

If capacity does not become available, the router returns HTTP `429`, sets `Retry-After: 1`, and uses `concurrency_limit_exceeded`:

```json
{
  "error": {
    "code": "concurrency_limit_exceeded",
    "message": "server at capacity for this model, please retry",
    "source": "router"
  }
}
```

Retry this error with bounded exponential backoff and jitter.

When a backend reports exact prompt usage, the router adjusts the active reservation by the difference between the estimated and actual input. Text-only samples also update the in-memory per-model estimator for later requests. The learned ratio resets when the router restarts; fallback estimates are not fed back into it, and image-bearing requests are not used for learning.

## Front-door shedding

Use `shed_if` to reject new work before queueing when the healthy serving pool is already under pressure:

```yaml
shed_if:
  kv_cache_utilization:
    gt: 0.90
  waiting_requests:
    gt: 20
```

The router averages each available signal across healthy agents serving the requested model. If any configured threshold fails, it returns HTTP `429`, sets `Retry-After: 1`, and uses `concurrency_limit_exceeded` with the message `model is under high load, please retry`.

Missing engine signals pass the gate. A single hot replica should normally be handled by per-agent `exclude_if`; `shed_if` is for pressure across the pool.

## Reserved and serverless modes

`mode` accepts `reserved` and `serverless`; omitting it selects `reserved`. The shared request and occupancy limits above run in either mode.

The current source also accepts these serverless key fields:

```yaml
api:
  mode: api-key
  keys:
    - key_hash: "<sha256>"
      key_preview: "sk-hivenet-...abcd"
      metadata:
        name: "Shared tenant"
        owner: "tenant-a"
      max_occupancy_share: 0.25
      quota:
        input_tokens_per_minute: 262144
        output_tokens_per_minute: 32768
```

These fields are enforced only when the effective policy uses `mode: serverless`:

- `max_occupancy_share` limits the key's in-flight footprint to that fraction of `admit_budget_tokens`. It does not apply `HIVENET_ROUTER_ADMIT_FRACTION` and rejects immediately with `429 rate_limit_exceeded`.
- `input_tokens_per_minute` is a continuously refilling one-minute token bucket charged at admission from the learned input estimate.
- `output_tokens_per_minute` is charged after a response completes. When the bucket is drained, the next request is rejected at admission. One response can drain at most one minute of capacity.

The input and output buckets are independent for each key-and-model combination. A zero value disables the corresponding cap.

<Warning>
  Dynamic keys have a stable key ID, so the three serverless controls are isolated per key. Static-key authentication does not currently populate a key ID; the handler falls back to `anonymous`. As a result, static keys share these B4 buckets and occupancy state for a model in the audited source. Do not describe them as isolated per-static-key controls until the runtime supplies a distinct static key ID.
</Warning>

For a static API-key configuration that can reach a serverless policy, startup fails when a nonzero `input_tokens_per_minute` is lower than that policy's `max_input_tokens`. The same cross-file invariant is checked during auth and policy reloads. `max_occupancy_share` must be `0` (unset) or greater than `0` and at most `1`.

The repository includes `auth.DeriveKeyDefaults` to calculate suggested B4 values from certified model limits. The router does not call this helper when loading `auth.yaml`; operators or provisioning tooling must still write the resulting values into the key configuration.
