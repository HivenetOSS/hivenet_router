---
title: "Using pi with Mycoroute"
---

This guide shows how to point [pi](https://github.com/earendil-works/pi) — an open-source coding agent (similar in spirit to Claude Code and OpenCode) — at a Mycoroute router. pi has first-class support for custom HTTP endpoints, so the integration is straightforward: pick the OpenAI-compatible API path and pi's underlying SDK handles `baseURL` + `Authorization: Bearer` for you.

> **Snapshot date — last verified 2026-06-09** (against `pi-coding-agent@0.79.0`).
> No time-bound caveats apply today; pi natively supports the router as shipped. Items in [Known limitations](#known-limitations) are tagged *time-bound* when relevant.

## What you get

- A coding agent (chat + file edits + tool calls) against any model in your fleet, with **no version-pinning workarounds**.
- Auth, quotas, and audit logging inherited from the router.
- OpenAI dialect end-to-end — your vLLM agents serve it natively, no schema translation.
- **No "background model" alias** to map — pi reuses the active model for compaction (unlike Claude Code's HAIKU or OpenCode's `small_model`), so there is no hidden second endpoint that might leak to a hosted provider.

## Prerequisites

- A reachable Mycoroute router with at least one `llm` agent registered.
- The agent's backend must serve `/v1/chat/completions` (vLLM does by default).
- A Mycoroute API key with access to the model(s) you plan to use.
- **Node.js ≥ 22.19.0** (pi's hard minimum — see [Common prerequisites — Node.js](/integrations/overview#common-prerequisites--nodejs) for `nvm` install/upgrade and the per-version-globals trap).

> **Tool-calling note (vLLM-side).** Once you start asking pi to *do* things (file edits, bash, custom tools), vLLM must be launched with tool-call parsing enabled or the calls are silently emitted as plain text:
> ```bash
> vllm serve <model> \
>   --enable-auto-tool-choice \
>   --tool-call-parser qwen3_xml      # or 'hermes' for Qwen2.5
> ```
> Chat-only sessions work without these flags, so you can defer this until you actually exercise tools.

## Step 1 — Install pi

```bash
# Preferred — uses npm directly, skips post-install scripts for security
npm install -g --ignore-scripts @earendil-works/pi-coding-agent

# Alternative — official installer script
curl -fsSL https://pi.dev/install.sh | sh
```

The binary is `pi`. Verify:

```bash
pi --version
```

### Disable telemetry and update-checks (recommended)

pi pings `pi.dev` for version checks and anonymous install telemetry. Both are easy to disable:

```bash
echo 'export PI_OFFLINE=1' >> ~/.bashrc      # disables BOTH (no version-check, no install telemetry)
export PI_OFFLINE=1
```

If you'd rather only silence the version check, use `PI_SKIP_VERSION_CHECK=1` instead.

> **What `PI_OFFLINE=1` actually does.** It suppresses **three** outbound behaviours: the version check at `pi.dev/api/latest-version`, the install telemetry ping at `pi.dev/api/report-install`, **and** the automatic download of pi's bundled search helpers (`fd` and `ripgrep`). The last point is what produces the harmless startup line you'll see in this mode:
>
> ```
> fd not found. Offline mode enabled, skipping download.
> ripgrep not found. Offline mode enabled, skipping download.
> ```
>
> pi falls back to OS file/text search and keeps working — chat, tools, everything functions normally. If you want the faster search helpers anyway, install them through your package manager (which is the right move for self-hosted setups since the binaries come from your distro, not from `pi.dev`):
>
> ```bash
> # Ubuntu / Debian
> sudo apt install fd-find ripgrep
> # then symlink so pi finds it under the name it expects:
> mkdir -p ~/.local/bin && ln -sf "$(which fdfind)" ~/.local/bin/fd
>
> # macOS
> brew install fd ripgrep
> ```
>
> After that, the startup lines disappear and pi uses the system binaries.

## Step 2 — Register the router in `models.json`

pi reads custom providers from `~/.pi/agent/models.json`. Create the file with the router as an OpenAI-compatible provider:

```json
{
  "providers": {
    "mycoroute": {
      "baseUrl": "https://<router-host>/v1",
      "api": "openai-completions",
      "apiKey": "$mycoroute_API_KEY",
      "authHeader": true,
      "compat": {
        "supportsDeveloperRole": false,
        "supportsReasoningEffort": false,
        "supportsUsageInStreaming": true,
        "maxTokensField": "max_tokens"
      },
      "models": [
        {
          "id": "Qwen/Qwen3.6-27B",
          "name": "Qwen 3.6 27B",
          "reasoning": false,
          "input": ["text"],
          "contextWindow": 131072,
          "maxTokens": 8192,
          "cost": { "input": 0, "output": 0, "cacheRead": 0, "cacheWrite": 0 }
        },
        {
          "id": "Qwen/Qwen3.6-35B-A3B",
          "name": "Qwen 3.6 35B-A3B",
          "reasoning": false,
          "input": ["text"],
          "contextWindow": 131072,
          "maxTokens": 8192,
          "cost": { "input": 0, "output": 0, "cacheRead": 0, "cacheWrite": 0 }
        }
      ]
    }
  }
}
```

### What each piece does (and the rules that matter)

- **`providers.<name>`** — `<name>` is an arbitrary id you pick. It becomes the `--provider` flag value and the prefix wherever pi references the provider.
- **`baseUrl`** — ends at **`/v1`**, not `/v1/chat/completions`. The OpenAI SDK appends `/chat/completions` itself.
- **`api: "openai-completions"`** — uses the OpenAI SDK, which automatically sends `Authorization: Bearer <apiKey>`. This is the path we want against the router.
- **`apiKey: "$mycoroute_API_KEY"`** — pi resolves `$VAR` from the environment at runtime, so the secret never sits in the file. (Also supports `${VAR}` and `!shell-command`.)
- **`models[].id`** — sent **verbatim** as the `model` field in requests. Must match exactly what an agent registers; check `/v1/models`.
- **`compat`** flags — explained below; the four above are the ones that matter for vLLM today.

### Why those `compat` flags

vLLM's OpenAI server doesn't speak every modern OpenAI feature. The four flags above match its current behaviour:

| Flag | Setting | Why |
|---|---|---|
| `supportsDeveloperRole` | `false` | vLLM only accepts `system`/`user`/`assistant` roles; pi defaults to the newer `developer` role for reasoning models. Forcing `false` keeps the role as `system`. |
| `supportsReasoningEffort` | `false` | vLLM's OpenAI server doesn't accept the `reasoning_effort` field — sending it would be rejected. |
| `supportsUsageInStreaming` | `true` | vLLM emits a final `usage` chunk when `stream_options.include_usage: true` is set. Keeping this `true` gives the router the exact token counts to deduct/audit. |
| `maxTokensField` | `"max_tokens"` | vLLM expects classic `max_tokens`; pi's default for reasoning models is `max_completion_tokens`. |

If you later want thinking/reasoning, set `reasoning: true` on the model and configure your vLLM with `enable_thinking` via `chat_template_kwargs`, then add `compat.thinkingFormat: "qwen-chat-template"`. Skip that today — chat works fine without it.

### Set the env var (case-sensitive)

```bash
export mycoroute_API_KEY="<your-mycoroute-api-key>"
```

Verify:

```bash
env | grep mycoroute_API_KEY     # exact case must match the config interpolation
```

## Step 3 — Set defaults in `settings.json`

Create `~/.pi/agent/settings.json` so pi starts on your model without needing `--provider`/`--model` every time:

```json
{
  "defaultProvider": "mycoroute",
  "defaultModel": "Qwen/Qwen3.6-27B",
  "enableInstallTelemetry": false
}
```

`defaultProvider` is the provider id from `models.json`; `defaultModel` is the model `id` from that provider.

---

## Step 4 — Verify

Sanity-check the router (bypassing pi):

```bash
curl -sS https://<router-host>/v1/chat/completions \
  -H "Authorization: Bearer $mycoroute_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen/Qwen3.6-27B",
    "stream": true,
    "messages": [
      {"role": "system", "content": "You are a helpful assistant."},
      {"role": "user", "content": "say hi"}
    ],
    "max_tokens": 64,
    "stream_options": {"include_usage": true}
  }'
```

If you get a streamed chat completion ending with a `usage` chunk, the chain is good.

Then pi:

```bash
# Non-interactive one-shot
pi -p "say hi"

# Pinned to a specific model
pi --provider mycoroute --model "Qwen/Qwen3.6-27B" -p "say hi"
pi --provider mycoroute --model "Qwen/Qwen3.6-35B-A3B" -p "say hi"

# Interactive TUI
pi
# Inside the TUI: /model opens the picker; Ctrl+L is the shortcut.
```

`pi --list-models` shows everything pi has registered.

## Discovering available models

The router publishes the live model list (aggregated across all registered agents) at `/v1/models`:

```bash
curl -s https://<router-host>/v1/models \
  -H "Authorization: Bearer $mycoroute_API_KEY"
```

Use whatever string appears there as the `id` of each model in `models.json` — case- and slash-sensitive.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Startup error: provider not found | `defaultProvider`/`--provider` doesn't match the key under `providers` in `models.json` | Same id in both places (case-sensitive) |
| `401` from router | Env var name mismatch (`$mycoroute_API_KEY` is case-sensitive) or wrong header | `env \| grep mycoroute_API_KEY`; the OpenAI SDK sends `Authorization: Bearer` automatically — no extra header should be needed |
| Backend rejects request with `unknown field reasoning_effort` / `unknown role developer` / `unknown field max_completion_tokens` | Missing `compat` flags | Set the four flags shown in Step 2 (`supportsDeveloperRole: false`, `supportsReasoningEffort: false`, `maxTokensField: "max_tokens"`) |
| Streaming returns but `usage` is absent | Older vLLM build without `include_usage` in stream tail | Set `compat.supportsUsageInStreaming: false`; router falls back to its own token meter |
| Chat works but tool calls have no effect (writes don't happen, bash doesn't run) | vLLM launched without tool-call parsing | Restart agent's vLLM with `--enable-auto-tool-choice --tool-call-parser qwen3_xml` (or `hermes` for Qwen2.5) |
| `model_not_found` from router | `models[].id` doesn't match what any agent registers | `curl /v1/models` and update the `id` |

### Reading the right logs

- **Router**: `docker logs gpt-router 2>&1 | grep -iE "chat/completions|policy|no eligible"`
- **Agent (proxy)**: `docker logs mycoroute-agent-<model> 2>&1 | tail -40`
- **Backend (vLLM)**: `docker logs vllm-<model> 2>&1 | tail -40` — request validation errors live here, not in the agent or router logs.

## Why we use the OpenAI path, not the Anthropic path

pi *also* supports `api: "anthropic-messages"` against a custom `baseURL`. It's a valid option, and the request shape is spec-correct (pi puts `system` as a top-level field, so it does **not** have the inline-`system` role bug that affects Claude Code 2.1.154+). Two reasons we recommend the OpenAI path anyway:

1. **No header gymnastics.** The Anthropic SDK sends `x-api-key` by default. To use `Authorization: Bearer` you'd set `authHeader: true` *and* override `x-api-key` to suppress it — workable but more moving parts.
2. **Lighter dialect.** vLLM's OpenAI-compatible server is its first-class endpoint; the Anthropic translation layer is thinner (and was the source of the recent Claude Code regression we worked around).

If you specifically want Anthropic-style prompt caching exposed by the router later, the `anthropic-messages` provider is the place — but today, `openai-completions` is the cleanest path.

## Known limitations

- **`max_tokens` ceiling.** vLLM enforces `max_tokens ≤ max_model_len − prompt_tokens`. The `models[].maxTokens` value in `models.json` is the upper bound pi will request; keep it well below the model's context window or you'll hit backend 400s on long prompts.
- **Streaming required.** pi *always* streams (`stream: true` is hardcoded). Your router and agents already handle SSE correctly post-deploy, so this is a non-issue today — but it means non-streaming-only backends are unusable through pi.
- **Backend 4xx responses currently bench the agent** via the router's `prev_failures` gate (router behaviour, not pi-specific). A malformed client can transiently take all agents serving a model offline. Durable fix is a router-side change to distinguish backend 4xx from agent failures.
- **`enabledModels` glob patterns** in `settings.json` filter which models the `Ctrl+P` cycle and TUI picker show, but do *not* restrict what `--model` can target. Don't rely on `enabledModels` as access control.
- **`/share` slash command** uploads the current session to a private GitHub gist. Opt-in / explicit — no automatic exfiltration — but worth noting if you handle regulated data: train people to know what `/share` does.
